建構設計師與工程師的溝通橋梁

《Design System 的設計心法 — 建立、彈性到加速成長》講座心得

Ossian Lin Published on Apr 2022

前言

對於 Design system 應該很多設計師都不陌生這個詞，也可能很多團隊也有引入使用，但對於工程師可能就沒甚麼概念了。本次參與了 IxDA 所舉辦的第二十小節互動快板，請來 awwrated 的創辦人 Harry Chuang 分享為他們公司設計到開發設計系統的心路歷程，以及對於如何建構能讓設計師跟工程師都通用、更能討論的 UI 元件庫平台。

關於 Design System 這件事

設計系統 Design system，從字面上來看就是為產品定義一套設計原則規範，裡面包含字型選用、字體大小、UI 元件等細節，最為知名的如 Google Material Design 以及 Human Interface Guidelines。設計師可以根據這個系統或是準則進行應用於這些作業系統上的對應設計，當然每家公司也都有著不同產品的設計系統，來讓自家產品達到一致性、建立和諧的使用者體驗，同時達到團隊需多人或跨部門協作。

根據講者的分享其實就是一個「收斂」，例如團隊將字體大小 14 定義為預設，正是給予 14 作為整個產品字體的預設值，也是讓數字有了意義。藉由將產品拆解的過程中找到重複利用的元件，進而拼湊成一個屬於產品的設計系統，來達到為團隊在討論開發上的一個「收斂」。

建構強大的 UI 元件庫

在過去學習無論是 Adobe Xd 還是 Figma 這類設計工具，相信多少都會用到「元件 Component」這個功能，就是個讓你在設計上可重複利用設計好的資料庫概念，跟大家常用的 copy-paste 不同在於使用元件可以不改動原始設計好的物件下廣泛利用於整個專案中需要重複出現、利用的地方。

對於設計師來說在設計上真的輕鬆許多，例如 Figma 的元件庫就能在同樣頁面下切換按鈕狀態，而不是額外製作一個新的狀態按鈕。這對負責程式開發的工程師來說這些 UI 元件能幫上甚麼忙？其實就如同設計師使用方式類似，只不過工程師在這上面是為了能用圖像化的方式更容易理解設計師所想要呈現的結果，有點像是在寫網頁前端時會去 Bootstrap 等官方網站找文件來看，裡面規範各元件的呈現方式及程式語法那樣。

本次講者提到的 Storybook 正是一個理想的建構 UI 元件庫平台，裡面除了可以定義設計師常用的規範外，還能加入程式碼讓工程師除了看懂圖像化外、同時也了解背後的程式碼，成為產品團隊的共通字典。

那麼，該如何起手呢？

從前面我們可以瞭解到設計系統對於設計師及工程師的實用性，以及建構一個讓雙方能用以溝通的平台是多麼有幫助又重要後，如何開始建構想必才是最根本的問題。畢竟如果不是公司指派下要額外去負責看上去挺龐大的平台，即便自願跳下來做也要讓團隊成員願意使用。

講者分享到當初在開始建構時花了不少時間「說服」所有人來達成團隊的「共識」，當大家都能理解平台的益處後才招募設計跟工程領域的成員開始著手建構。對於團隊第一次做設計系統沒有頭緒方向下可以選擇參考其他公司的設計系統，像是講者就很推薦從 Ant design 做參考，初期先不要複雜化、專注目前專案常用的元件，洞察可共用的元件及元素，並系統化命名、給予基本的定義規劃。

當然團隊的設計系統也不太可能一成不變，可能會隨著產品的改版等作調整，保持元件結構化及彈性化能當結構越清楚時可演變出更豐富得運用，例如用於不同裝置端，搭配平台可以直接做測試及確認，來提升團隊協調通。因此沒有絕對的設計系統，讓平台保持彈性、學習曲線不要太高，來避免導致只有部分人使用的窘境。

後記

過去在開發產品的經驗中，不論是設計師還是工程師都沒甚麼在管設計系統或是版號，當天聽了 Q&A 後覺得當時來說是算正常的，畢竟人力跟時間上都是個問題，一般來說都還是會先專注於現行產品的開發完，之後才回頭想這些。

藉由這次的講座，更瞭解到設計系統能如何在設計師跟工程師兩者間運作，尤其是能夠建構出一套 UI 元件庫平台讓整個產品團隊有效溝通，這項雖然是個大工程但對於產品團隊其實都是必經之路，否則當未來產品線龐大時在設計上很難有一套規則外，對於現行開發上要在各裝置平台轉換也都需要設計系統來維持產品的一致性呢！
