📝Soking 老師週報心得(2024/01/15)

本週主題：產品需求文件 PRD 的應用難題

Ossian Lin Published on Jan 2024

前言

2024 年 1 月第三週週報，最近天氣變化大各位保重...

產品需求文件(Product Requirement Document，簡稱 PRD)，應該部分讀者在工作上會聽到、甚至親自撰寫用於整個產品開發前的需求整合文件。裡面自然會有「需求」和一些簡單說明，可以幫助團隊釐清思緒、對齊方向等，讓溝通上更為方便。

嗯，聽起來挺棒的，但對於多數人聽到這份文件可說是非常討厭的，為什麼呢？Soking 老師分享到人在有限的記憶下，被一整天的會議轟炸後才來撰寫，通常都非常吃力，以至於產出的文件給團隊其他人來看，覺得不如當下開會討論，又進入了惡性循環。另外，每間公司或團隊也都有各自的寫作習慣，甚至需求未定下撰寫時常修改，對於撰寫上都困難重重。

接下來就跟著 Soking 老師本週週報，一起認識如何寫出一份好的產品需求文件，避免落入上述這種不良的情況吧！

明文依據下的討論及開發

相信各位讀者應該有經驗，在未明確的需求下規劃執行工作是如履薄冰，何況經常都要評估時程與難度，此時若有一份需求描述明確的文件時，通常可以幫助團隊迅速對齊目標，在清楚的條件下討論合理的解決方案。尤其軟體需求的溝通經常是很抽象或複雜邏輯的議題，如果還參雜使用情境加入討論，藉由需求文件能瞭解到有哪些條列的需求來輔助討論。

當我們投入於解決問題時，也很常迷失於細節中。通常我們會著重於探討「為什麼要做」，對於那些「經過思考決定不做」的則很容易就忘掉，畢竟能解決眼前問題乃當務之急，能少一事算一事。Soking 老師提到有時候當初決定不做的事，只是因為階段性的考量，待時機成熟後則可能會在納入考量。然而如果忘記當時的考量及理由，到後來突然要動工時，很容易發生「一開始就說好不做，為什麼現在又要考慮」這種聲浪反彈。如果當時的 PRD 文件有記錄下來，這時候就成了能幫助團隊快速聚焦目標、喚起過去決策及評估記憶的最佳幫手。

更容易地對焦彼此

通常來說工作任務不會只有一項交辦給我們，可能同時有 2~3 項在同步進行，即便有明確的優先度順序讓我們能安排，但有時候還是會有同時或同一天進行討論，在這樣與超多人對齊產品需求、甚至最基本的認知問題，若每個人都像第一次聆聽般不停丟問題打斷會議，就很容易形成「整天都在開會卻沒甚麼工作進度」的錯覺。而且各位應該也都有經驗是會議當天原本的負責人無法出席，對於當時的議題沒辦法給予即時解惑，這樣也很容易導致整體開發進度耽擱。

對此 Soking 老師就建議平時花點時間去維護 PRD 文件，將已經達成共識的部分有條理或視覺化的記錄下來，讓後續閱讀者或是用於討論上都能快速 recap 資訊，甚至老師還是丟出線上連結方式，告知對方需要的情報怎麼尋找。記得第一次比較認真在寫 PRD 文件遇到不少問題，也不是說挫折、比較偏向學習各公司團隊文化。同樣給出兩份 Figma 設計稿的連結，當時會被要求每個畫面相關的邏輯都要寫明，因為 IT 只會對焦流程圖，而非連同切版、額外文件交錯閱讀，因此寫 PRD 文件時就會陷入一種好像在做重工的狀況。同時要同步兩份文件需求外，還有可能需求及流程隨時變化的情形，讓我還在摸索是否有更好的工具來改善這個工作模式。

因為 IT 真的是只給我看流程圖，一堆輸入檢核邏輯完全 let it go~ ¯\_(ツ)_/¯

產品團隊知識資產管理

前面提到文件能幫助我們在未來能更快速的對焦或回顧問題，然而總會有文件內的資訊無法滿足或是解決的問題，這時候可能是有新問題產生。隨著時間推移，需求可能因為時機成熟而有了變更，也可能單純業務需求而改變，但 PRD 文件可能未更新到這些有影響的部分。因此我們就要花點時間去檢視過去的需求內容，除了喚起塵封的記憶或重現當時議題外，也能立基於這些已有的條件下去解決新的需求。

產品開發整體時程並非短期衝刺，更何況有許多公司並未正確引入敏捷衝刺等開發方式，通常一件事情即便每日持續緊追都至少還是會有幾個月、甚至長則年度來計算。這意味著當時的需求可能隨著時間演進而跟不上腳步，又或是本來就不是件好案子而負責的人員早已有所變動，如果沒有銜接好然後隨便找個接棒的來負責回答，要對方能思緒清晰地把來龍去脈講清楚，可想而知是件困難的事。

之前曾被交辦過將一堆塵封已久的 bug 整理並請相關人員驗收後關閉，畢竟年份久遠至 2014 年開立，若該項 bug 持續未關閉那代表著自家的產品有著漏洞，而且還持續未做處理。然而在整理及會議討論過程中會發現，許多當時開立單據的負責人早已調動，要翻出當時的 PRD 文件也是件難事，何況每個人寫的方式還不同。對此我們只能試著從當時開立的內容去抽絲剝繭，嘗試重現該問題或是與現行的產品去檢視是否早已不付存在，同時從自己內部團隊開始，在後續的 PRD 文件撰寫上都盡可能地將內容可視化，以利於後續在溝通上能有所依循、順著理路進行討論。

後記

本週 Soking 老師分享了關於 PRD 文件的難題，其實老師在去年 6 月的週報也有提過 PRD 文件，只是當時並未深入講解。不論是什麼樣的文件，最重要的首要目標就是可讀性，一份易懂好理解的文件能勝過幾十頁圖文並茂的投影片。除了撰寫好文件的重要性，也要隨時去維護及管理內容，確保有更新最新、最終的版本，以避免未來回頭查看時落入如同技術債的步塵。

個人在撰寫 PRD 文件上比較像是過往繪製流程圖，畢竟自家 IT 只會跟著流程圖去開發，相關需求邏輯經常是不會自行在做打開確認。因此在繪製時必須很明確地將許多資訊詳盡紀載，以避免開發後測試時認定為 bug 而花時間對齊需求。然而這並非彼此協作上的最佳解，如果能夠利用流程圖達到多方對焦、同時作為一份有力的 PRD 文件供他人閱讀，或許這確實是在不改變他人習慣下的方便解法，對此我想也只能持續摸索與學習了！

Take away:
1. 大家都害怕不確定性，加上每個人的記憶其實都不太好，明文紀載需求內容有助於穩定目標。
2. 我們很常做完一件子就忽略回頭維護PRD文件，某種程度上這也是一種技術債的累積。
3. PRD文件可視化有助於團隊知識資產的管理與對齊，讓討論上能更為清晰。

以上，我們下週見，啾~
