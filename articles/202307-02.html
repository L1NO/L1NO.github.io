📝Soking 老師週報心得(2023/07/24)

本週主題：產品需求文件 PRD 到底要寫到甚麼程度？

Ossian Lin Published on Jul 2023

前言

2023 年 7 月第四週週報，又是忙碌的一週，Deja vu！

前陣子一度被指派需要負責撰寫產品需求文件(Product Requirement Document，PRD)文件，主要是針對某功能下半年規劃開發所需，然而在過去經驗上認真來說好像沒寫過正式的 PRD，因此開始上網找資料尋求解答，實際發現沒有真正的系統化或參考格式；沒有參考依據對於這份文件該寫多詳細、如何讓其他人能看懂，自然就成了一大難題。本週 Soking 老師就來為各位介紹 PRD 應該有哪些元素、如何撰寫，以及大家最在意的如何讓其他人也能閱讀理解。

接下來就跟著 Soking 老師本週週報，一起來學習如何撰寫一份合宜的產品需求文件吧！

PRD 文件的目的

就一個菜鳥從字面來看，PRD 大概是個把功能、規格、需求等重要資訊寫清楚的文件，概念是對了但實際上還要說明需求發生的來由、期望產生什麼效益，以利於後續解決方案證明是否滿足需求，並在多次迭代後才能完善，為的就是有明確的方向，畢竟有太多時候是為了手段而拋棄目的的決策。

Soking 老師解釋優秀的「需求」往往要有一些抽象的空間存在，這樣才能既指名方向，又不限制非要用什麼手段來實現不可，好讓實現需求的團隊能依據現實狀況來提供對應解決方案。例如收到業務開發新功能的需求，目的是為了協助客服人員能同步查詢客戶身分別，因此提出開立新欄位來註明客戶身分，然而當前客戶資料呈現已過於繁雜、新增欄位並無法有效解決，經討論後改以圖示呈現。

不過人腦對於抽象目標的理解容易扭曲成更簡單具體的東西，因此透過寫下 PRD 文件來幫助我們找出一種說法，既可以描述抽象的目的，還為了防止我們的記憶混亂，避免因為與不同的利害關係人討論，就迷失了原本的方向。

PRD 文件的用途

接著讓我們探討這份文件的用途，初期認知 PRD 應該是寫給工程師的溝通文件，讓對方能理解我們想要的設計需求；不過在龐大的組織中不只如此，還要考慮到其他串接部門是否也能理解我們要開發的東西。可能跟過去都是小團隊共事、需要串接的資料較少，因此在撰寫上少了許多考量，例如交易是否回傳後端金流讓帳務能接續記帳。

聽起來寫完這份文件理應閱讀的人就知道前因後果、該怎麼接續，如同一份文獻+說明書能銜接。然而，人跟人之間光是溝通過程就會有認知落差，想靠這份文件彌補，則必須根據當時的人、時空背景，來調整溝通的顆粒度以及溝通的進度。因此 PRD 文件第一個最好的讀者其實是撰寫文件的我們，藉由這份文件讓我們能在需求會議上作為參考資料、降低認知負擔，在有限的認知資源下溝通議題。

在幾個小功能更動上，不時會需要我負責製圖讓大家能了解改哪些地方、大概長怎樣，經過 2～3 次拉攏相關有串接的部門於會議上提出疑惑及各自需求、甚至一些建議後，這份 PRD 才會逐漸完善。即便只是我們單位提出的 PRD，它匯聚了這次案件中相關部門的意見及需求，讓彼此在撰寫上能更清楚需要顧慮到哪些因素，而有一致的方向；反之，當需要回去翻資料時，許多時候都會詢問在職同仁才知道為什麼當時會有這樣的需求，畢竟許多時候一項需求的出現可能不是我們想的這麼單純。

PRD 文件的內容

認識了 PRD 文件的目的跟用途後，接著就是開始撰寫內容的部分。誠如前言所提到，剛開始接觸自己寫 PRD 文件在網路上摸索半天，最後都回歸到一個問題點：「PRD 到底要寫到什麼程度？」寫的超級詳盡許多時候可能是我們空想盤點出的內容，即便有這樣的問題存在許久，可能在過去早已達成共識先置之一旁。如果只寫得太過粗淺，則會讓其他閱讀者無法理解我們想表達的真正需求、議題，甚至久了其實也很難喚起當時記憶。

Soking 老師將 PRD 文件內容分為四塊來探討：「設計目的」、「目標情境」、「實踐規則」與「描述解決方案」。「設計目的」最容易理解，也最不容易寫得好，在文件目的時提到「需求描述」必須帶有一點抽象空間，既指名方向又不定義具體的解決方案；「目標情境」是定義參與系統運作的角色及任務，這部份依賴任務步驟的分析，將抽象的大目標轉換成數個小目標，並且定義每個小目標的任務步驟。

「實踐規則」包括具體的任務案例，描述解決方案應該要在指定的情境中滿足的條件，用個簡單解釋就是「有沒有符合我們的假設」這麼單純，以老師的說明為「硬指標」，不涉及好用不好用的體驗流程。例如最近情境測試「不可重複使用折抵券折價停車費」，從字面來看「只能使用一張折價券」這件事就是「硬指標」，預測結果應該只有「阻擋使用者刷第二張」，使用折價券的流程設計或告知介面資訊很糟糕就是另外一個議題了！

有趣的是通常人們都會有同理心或過往經驗映射，對於當下的假設情境及預測結果提出意見，尤其是「使用者體驗」。以上述舉例對於工程師來說已滿足基本需求(e.g. 它有阻擋)但介面告知資訊超不明顯，像這樣會涉及實體環境的工作流程，那麼最首要應該是先與業務或主導者確認情境邏輯可行性，再整理數位環境與實體環境的服務流程，讓「實踐規則」得以運作。

最後「描述解決方案」這邊會定義為了滿足使用者案例所需要的功能或資訊內容，簡單來說就是整件事所需的資訊。個人經驗通常發生在軟體產品功能，例如新增支付服務流程，個人最常做就是畫 Functon flow 流程圖，把需要的資訊標註上去(e.g. 當回到此頁面需刷新資料)、描述解決方案的運作邏輯。另外，Soking 老師有提到將解決方案中會需要的資訊內容，進行結構化的分析，整理成資訊架構規劃的內容。在需求訪談的過程藉由畫出 iA 的示意圖，讓抽象的資訊架構能夠視覺化，以搭配案例情境來討論。

後記

經過多次需求文件撰寫經驗下，讀完這週 Soking 老師的解說，算是將 PRD 文件撰寫方式有更明確的方向跟概念，尤其有些案例除了撰寫文件外，還投入實作更能理解 PRD 文件的重要性。本週個人認為最重要的部分在於「內容」這塊，因為多數人很常會有「PRD 到底要寫到什麼程度？」狀況發生，藉由老師提的四個核心要素能讓我們在撰寫上更有方向。其中「目標情境」及「實踐規則」兩項應該是最為廣泛應用，如果需要做測試那就需要先歸化測試情境，而做測試也需要一個指標來驗證，因此針對這兩項下手會是 PRD 文件撰寫上最好的切入點。

Take away:
1. PRD 文件的目的是「定義方向」，描述抽象的目的，避免我們隨著時間而記憶混亂。
2. PRD 文件用途主要是協助我們降低認知負擔，讓我們在溝通會議上能快速提出需求及參考文獻。
3. 藉由老師分析的 PRD 文件四項內容能有助於我們在撰寫時不知方向時的指引。

以上，我們下週見，啾~
